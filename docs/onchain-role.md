# 04｜链上角色：链上撮合 + CCD 结算

## 项目定位

**Agent-to-Agent 动态竞价与交易撮合：由 Concordium
智能合约执行公开、确定性的竞价撮合规则，并完成 CCD
结算；链下应用基于真实成交记录生成市场价格信号。**

## 1. 链上发生的是哪个动作？

**核心动作：竞价、撮合、CCD 支付与结算。辅助动作：成交记录。**

Concordium
智能合约不是一个事后记录日志的审计层，而是交易规则的实际执行者。MVP
中，以下关键步骤发生在链上：

1.  **创建拍卖。**
    卖家提交服务标识、单轮可交付容量、最低接受价格和竞价截止条件。
2.  **提交报价。** 买家 Agent
    直接向合约提交报价。为降低中标后拒绝付款的风险，MVP
    要求买家把报价金额存入合约；报价同时表示买家的最高总支出上限，已经覆盖可能由买家承担的平台费。
    这笔资金在拍卖结束前由合约暂存。
3.  **执行撮合。**
    竞价结束后，合约过滤低于卖家底价的报价，按报价从高到低排序，最多选择与服务容量相同数量的赢家。报价相同时，使用合约定义的确定性规则（例如更早获得的链上报价序号）打破平局。
4.  **计算成交价。** 对每个中标报价，当前演示暂按
    `成交价 = (买家报价 + 卖家本轮底价) / 2` 计算。中点定价是初步方案，后续可以调整；
    但每轮实际采用的规则必须在报价前公开并固定。
5.  **CCD 结算。**
    交易剩余为 `赢家报价 - 卖家底价`。若交易剩余小于成交价的 10%，不收平台费；否则平台收取
    交易剩余的 10%，由买卖双方平均承担，刚好等于免收阈值时仍收费。合约必须保证
    `成交价 + 买家平台费 <= 赢家报价`。赢家收到未使用报价退款，未中标者退回全部报价；卖家平台费
    从成交款中扣除。网络手续费另计。平台收款地址和费用规则不能在拍卖开始后修改。
6.  **记录成交结果。**
    合约状态或事件记录拍卖标识、赢家、成交价格、手续费和结算状态，便于参与方及评委查询。

**报价隐私边界：** MVP
采用公开报价。链上报价和相关交易输入可能被其他参与者观察，因此不承诺密封竞价或对中介保密。若未来需要密封报价，可另行评估
commit-reveal 等机制，但不纳入三周 MVP 的交付承诺。

**链下负责：** Agent
的报价策略、服务详情页面、交易流程界面、历史成交统计和价格信号展示。价格统计应基于已确认的链上成交，而不是中介自行声称的结果。

## 2. 对应 3.2 里的哪一条理由？

**核心理由：多方互不信任，需要一个中立的结算或托管方。**

买家、卖家和中介的利益并不完全一致。买家希望按约定价格成交，卖家希望获得应收款，中介希望按照公开规则收取费用。

如果撮合和资金结算全部由中介的中心化后端决定，参与方就需要相信中介没有暗中改变赢家、成交价格或手续费。将报价输入、撮合规则和
CCD 分账写入 Concordium
智能合约后，参与方可以检查部署的规则，并核对链上执行结果，不必只相信中介后台返回的成交信息。

本项目还对应 3.2 中"比赛要求使用指定链"的理由：Concordium
不只是用来存放一个交易哈希，而是直接承载竞价输入、撮合执行和资金结算。

需要明确：链上执行只能保证合约按部署代码运行，不能自动证明规则在经济学意义上公平，也不能证明卖家实际交付的服务质量符合要求。规则本身仍需测试、审查和清晰披露。

## 3. 去掉链上这一步，项目还剩什么？

去掉链上后，项目仍可保留：

-   买家 Agent 与卖家 Agent 的模拟和报价策略；
-   竞价排名、容量分配和成交价格计算；
-   中介费用计算；
-   历史成交价格统计和价格信号面板；
-   交易流程的 Web 界面。

这些功能可以由普通后端实现，因此项目不应声称动态竞价或价格发现只能依靠区块链。

但去掉链上撮合与结算后，项目会失去核心差异：

-   参与方无法仅凭公开部署的合约和链上输入核验赢家及成交价是否按规则产生；
-   中介后台可能成为唯一可信的撮合结果来源；
-   CCD 支付与拍卖结果无法由同一套链上规则直接关联；
-   参与方无法独立核对合约执行的资金分配结果。

因此，链上不是可选的日志或审计层，而是本项目核心交易协议的执行层。链下应用负责让
Agent 易于参与，链上合约负责执行竞价、撮合和结算规则。

**实现状态边界：** 当前已部署并验证的 spike 合约仍采用双方各固定 0.2 CCD 的旧费用规则。
按交易剩余收费、只锁入报价金额以及双买家 Testnet 闭环仍需实现和重新验证。

## 4. 评委在哪里能看到链上这一步？

演示界面将提供从竞价到结算的完整路径：

1.  **拍卖创建记录：** 服务标识、容量、卖家底价和截止条件。
2.  **链上报价记录：** 各报价对应的交易哈希及报价状态。MVP
    报价公开，界面会明确说明这一点。
3.  **撮合结果页面：**
    中标者、成交价、未中标结果，以及合约使用的定价和排序规则。
4.  **结算明细：** 买家支付金额、卖家实际收到的
    CCD、中介手续费、退款金额和结算状态。
5.  **区块浏览器链接：** 对应的 Concordium
    测试网交易详情，供评委核对真实交易和资金转移。
6.  **价格信号面板：**
    由已确认的链上成交记录计算近期中位数、价格区间和成交样本数量。样本不足时显示提示，不把模拟数据伪装成真实市场数据。

理想的现场演示是：创建一轮拍卖 → 多个买家提交报价 → 合约执行撮合 →
合约完成 CCD 分账和退款 → 打开区块浏览器核验 → 价格面板更新。

## MVP 边界与风险

-   只实现单卖家、单轮拍卖和有限数量的买家；优先支持固定容量与固定定价公式。
-   不实现多轮自主议价、零知识证明、密封竞价、复杂交付仲裁或生产级争议处理。
-   如果采用报价附带 CCD
    的方式，必须测试未中标退款、中标者差额退款、重复结算和失败交易等路径；不要在未测试资金边界前部署真实资产。
-   中介手续费规则必须在拍卖创建或协议配置时明确，设置合理上限，不允许在结算时任意修改。
-   价格信号是特定服务规格、时间窗口和撮合规则下的成交统计，不等于普遍适用的"公允价值"。
-   智能合约代码必须经过测试；部署后如需修改规则，应明确采用新版本合约或新的拍卖实例，不应暗中改变已创建拍卖的规则。

**一句话总结：买家报价、竞价撮合、成交价格计算和 CCD 结算由 Concordium
智能合约执行；链下 Agent
应用负责策略与交互，并根据已确认的链上成交生成市场价格信号。**
